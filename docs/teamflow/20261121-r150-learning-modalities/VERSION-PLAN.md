# 学习多形态化：功能版本规划（r150）

> 状态：**已评审通过**（2026-11-21，产品负责人确认按 M1 → M2 → M3 → M4 顺序推进）。
> 本文只做规划与取舍；M1 已落地的部分（口播稿数据模型、脚本质量闸、3 章黄金稿）见同目录 `TECHNICAL.md`。
> 目标读者：产品负责人。看完应能回答「先做哪个版本、每个版本交付什么、卡在哪里」。

## 1. 要解决的问题

站内教程是纯阅读形态：60 章 / 618 个内容块（正文 165、列表 106、代码 64、提示 141、表格 77、问答 60、演示 5），
正文约 6.7 万字。对「不想读长文本、看到代码就跳」的工程师，当前只提供一个入口。

**前提判断**：这不是人格差异，是**场景差异**——通勤、睡前、面试前一晚、写代码卡住时，
同一批人需要不同通道。

**但表征必须按内容类型分派，不追求全覆盖**（2026-11-21 修正，取代初版「每章四种表征」）：
代码 / 语法 / 界面类章节念不出来也记不住，音频对它们是**负收益**；反过来，纯代码沙箱对
「分布式一致性」这种抽象概念也没用。每章声明它需要哪几种表征，而不是每章都塞四种。

### 3.1 内容可听性分级（2026-11-21 新增，取代「全量 60 章」口径）

**判据不是代码占比**：全站仅 64 个代码块（占全部内容块 10%），单章最高 29%（`fe-ts-advanced`），
其余多在 8–12%——代码块只是点缀，区分度不够。真正的判据是**「这段内容能否脱离视觉独立成立」**。

| 层 | 特征 | 典型章节 | 表征组合 |
|---|---|---|---|
| **A · 复杂概念** | 有清晰因果链，需要连续推理，无必须盯着看的结构 | `be-distributed-consistency`、`cs-io-model`、`cs-process-thread`、`mw-message-queue`、`ai-llm-basics` | **听 + 比** |
| **B · 常见场景** | 有过程、有冲突、有「错误做法 → 后果 → 正确做法」 | `mw-observability`、`eng-incident-capacity`、`mw-cache-strategy`、`be-rate-limit-resilience`、`eng-tech-debt` | **听（对口）+ 做** |
| **C · 必须看** | 语法、API、布局、命令、可视结构；听了记不住 | `fe-ts-advanced`、`fe-css-layout`、`be-go-concurrency`、`sql-window-explain`、`ai-langchain-langgraph`、`mw-docker`、`algo-sorting-stability` | **读 + 做**（不做音频） |
| **C′ · 算法演示类** | 需要看过程推进，但可听觉辅助 | `algo-complexity`、`algo-hash-pointer`、`algo-binary-tree`、`algo-dp-graph` | **做（主）+ 比**（不做音频） |

结论（2026-11-22 实测校准，全库 **60 章**，分层单点在 `frontend/src/content/spoken/coverage.ts`）：
- **可听子集 45 章**（A 29 + B 16），C 11 / C′ 4 不做音频；音频体量按 45 章折算约 **95–115MB**
- C 类章节的「听不了」不是缺陷：它们的正确解法是三档代码展开 + 可执行演示（见 §4 插队项）
- 任何章节如果口播稿写不出「因果链」或「场景」，就该被判回 C 类——**这是脚本阶段的质量闸，也是止损机制**

## 4. 版本路线

版本号用里程碑 M1–M4 命名；实际 `vX.Y.Z` 在发版时绑定（`dev` 上 r118–r147 存量若先发 v0.5.0，则本规划顺延为 v0.6.0 起）。

### M1 — 听：链路打通 + 3 章试点

**目的**：用最小成本验证「离线音色 + 情绪烘焙 + 句级跟读」到底好不好听。**这是一个止损点**——选型错了在这里改，不要铺到 40 章再发现。

范围：
- 口播稿数据模型（`SpokenScript`：句级文本 + 情绪标签 + 停顿），只做 §4.1 的 3 章
- 离线工具链 `scripts/tts/`：合成 → VAD 切句 → 时间轴 JSON → 质检报告（响度、断句、时长）
- 音频分发通道：不进 Git，nginx 挂载 `/audio/` 目录，`scripts/deploy-audio.sh` 增量 rsync
- 播放器：播放/暂停、倍速 0.75–2.0、**句级高亮（可关闭）**、断点续听、MediaSession（耳机键 / 锁屏元数据）
- **泛听模式**（磨耳朵场景的核心，2026-11-21 追加）：本节循环、整章连播、跨章自动续播（像播客），
  播放时预取下一小节；UI 显示「已听 N 分钟」而不是「还剩 N 分钟」——倒计时本身就是压力
- 文案基调：入口叫「听听」不叫「课程」，不用「学习任务」「进度考核」这类词
- 入口：`/learn/:chapterId?mode=listen`，记忆上次所选模式
- 进度：`LearnChapterProgress` 新增 `heard` / `listen_section_id` / `listen_position_ms`（**契约双改**）
- 「听过」语义：听到小节末尾即计入 `seen`（与「读过」同一语义），`heard` 只用于区分来源——报告页「已读完 N 章」逻辑不改

验收：
- 3 章可完整听，句级高亮偏差肉眼不可察
- **关闭高亮后页面不再跟着滚动**（磨耳朵时不看屏，滚动本身就是干扰）
- 跨章自动续播切换间隙 ≤1.5 秒，3 章连听不断流
- 断点续听恢复误差 ≤ 3 秒
- 气隙部署（`RADAR_OFFLINE=true` + 无外网）下可正常播放
- `test_r115_intranet.py` 零新增登记项
- 音频体积 ≤ 10MB（3 章）

**卡点**：需要一次性 GPU 环境（见 §6）。

#### 4.1 试点三章（2026-11-21 修订：全部落在 A / B 类，不再含代码密集型）

| 章节 | 层级 | 叙事形态 | 为什么选它 | 它能验证什么 |
|---|---|---|---|---|
| `be-distributed-consistency` 分布式事务与最终一致性 | A · 最抽象 | 单口 + 类比 | 全站最难「用嘴讲清」的概念，没有之一 | 口播稿的能力上限：抽象概念能不能脱离图讲明白 |
| `mw-observability` 可观测性与线上排障 | B · 纯场景 | 对口（逗捧抬杠） | 天生有过程、有错误做法，逗哏一开口就能装懂 | 双人抬杠能不能不尬；包袱是否真能笑出来 |
| `mw-cache-strategy` 缓存与失效策略 | A+B · 混合 | 单口 | 概念 + 场景（穿透 / 击穿 / 雪崩）都齐，因果链长 | 同一章内概念段与场景段的心智切换是否顺滑 |

选型逻辑：这三章覆盖「最抽象 / 最叙事 / 混合」三种最难形态，**且都通不过就该重新考虑音频这条线是否值得做**。
它们都不含算法演示、代码块占比 9–11%，是最公平的音频试金石。

**已排除**（初版曾选，现撤销）：`algo-hash-pointer`、`be-concurrency-idempotency` —— 前者靠演示更有效，
后者是代码密集型，念出来记不住，属于 C 类。

## 5. 有声书技术方案（关键决策）

### 5.1 口播稿 ≠ 原文

原文有 64 个代码块、77 张表格，TTS 念出来是灾难。必须新增 `SpokenScript`：
代码转述为「这段代码在做三件事：先……再……最后……」，表格转述为对比句。

**听模式渲染的是口播稿文本，不是原文**——句级高亮高亮口播稿。原文只在读模式出现。这样文本与音频严格一一对应，不需要跨结构对齐。

### 5.2 情绪体系

7 类闭集，句级标注，来自口播稿生成阶段（LLM 同时输出结构与标签）。
**这 7 类是按「相声表演」设计的**（2026-11-21 二次修订，取代初版的讲解腔标签）：

| 标签 | 语义 | 停顿（前/后，ms） | 声音特征 |
|---|---|---|---|
| `banter` | 闲聊铺垫（默认） | 0 / 160 | 语速偏快、音量偏轻，像真在聊天 |
| `setup` | 一本正经地下结论（多半是错的） | 200 / 260 | 笃定、不犹豫，越肯定越好笑 |
| `deadpan` | 冷面拆台（"嗯？"） | 350 / 400 | 短、平、不带情绪——捧哏的力量全在「不演」 |
| `punch` | 抖包袱 | 450 / 700 | 前紧后顿，最后一个字咬住 |
| `realize` | 恍然（"哟"） | 500 / 600 | 短促、音调上扬后骤停 |
| `contrast` | 转折（其实不是这么回事） | 420 / 200 | 前半轻、后半压下来 |
| `wrap` | 收束（这段记住一句话） | 400 / 800 | 放慢、落地 |

强度由全局 `emotion_gain`（0–1，默认 0.55）统一缩放。
**相声的阈值比讲解高**：讲解怕朗诵腔所以压到 0.4，相声需要表演性，0.55 起；但**笑点靠文本节奏，不靠音量**——
把 `punch` 演成喊叫是最常见的失败。

### 5.3 合成与切片

1. 按**情绪段**（同情绪连续句）整段合成，保证段内韵律连续
2. 段内用 VAD（silero-vad）检测 >250ms 静音切句，得到**采样级准确**的句边界——不需要 ASR 强制对齐
3. 段间按 §5.2 插入设计停顿
4. 输出：**每小节一个 m4a**（1–3 分钟）+ 一份 `timeline.json`（句起止 ms + 文本索引）
5. 文件数约 240 个，单文件 0.5–1.5MB

选「每小节一个文件」而非「每句一个文件」：文件数可控、天然支持 Range 拖动、断点按 ms 记录；
句级精度靠 timeline 提供，不牺牲体验。放弃「整章一个文件」是因为首屏要拉 4MB 以上。

**对口章节的额外处理**：`timeline.json` 增加 `speaker`（`dou` 逗哏 / `peng` 捧哏 / `narrator`）。
按「发言段」合成——同一 speaker 连续的多句一次合成，不同 speaker 之间换音色，段间保留
**250–450ms**（比讲解短：相声本来就接得紧，超过 500ms 包袱就凉了）。前端按 speaker 分色显示台词，
不按角色分左右栏（窄屏放不下）。

**捧哏是合成难点的解药**：捧哏台词短（"啊？""真的假的""您等会儿"），几乎不需要长韵律控制，
是整个音频里最容易合成得自然的部分；真正难的是逗哏的长段落，而它只需要 `banter` 一种主要音色。


### 5.4 音色选型（收敛顺序已定，M1 实测终稿）

| 模型 | 许可 | 中文 | 情绪控制方式 | 备注 |
|---|---|---|---|---|
| CosyVoice2-0.5B | Apache-2.0 | 强 | instruct 自然语言指令 + 细粒度标记 | **首选**，情绪指令最直接 |
| IndexTTS-2 | Apache-2.0 | 强 | 情感与音色解耦，独立情感参考音频 | 备选，情绪漂移大时用 |
| MegaTTS3 | 需核实 | 强 | 依赖音色参考 | 音质好，推理较重 |
| GPT-SoVITS | MIT | 强 | 依赖参考音频 | 生态成熟，长文本拼接易抖 |
| Kokoro-82M | Apache-2.0 | 弱 | 极弱 | 仅 CPU 兜底用 |
| ChatTTS | **CC-BY-NC** | 中 | 韵律标记 | ⚠️ 非商用许可，本产品有商业化可能，**排除** |

选型标准不是"哪个最像人"，而是**「同一音色在 7 类情绪间切换时是否稳定」**——这正是 M1 试点要回答的问题。

**本机 GPU 口径下的收敛顺序**（已定用本机生成）：

1. **CosyVoice2-0.5B**：先跑通。instruct 模式让 §5.2 的 7 类标签能一对一映射成自然语言指令，不需要为每种情绪准备参考音频。
2. 若显存不足或情绪切换时音色漂移：改 **IndexTTS-2**（情感与音色解耦，情绪换而音色不变），代价是每种情绪需一段参考音频。
3. 两者都不可行才考虑 GPT-SoVITS（生态最成熟，但长文分段拼接容易在段边界抖），并把情绪收敛为「语速 + 停顿」两个维度。

显存门槛仅供参考，以本机实测为准：0.5B 级模型含参考音频编码通常 4–6GB 可跑；8GB 以下建议先试 FP16 或量化版，不要直接上 1.5B 以上模型。


### 5.5 资产分发（不破 C7）

- 音频**不进 Git、不进镜像**：镜像层不带 95–115MB 音频，避免改一行代码重建大层
- nginx `location /audio/` 指向挂载目录，`expires 30d` + Range
- 公网：`scripts/deploy-audio.sh` rsync 增量同步
- 内网/气隙：`audio-pack-vX.tar.zst` 离线包 + 校验和
- 前端一律用相对路径 `/audio/...`，内网与公网同一套代码
- dev 环境：Vite 代理 `/audio` 到本地目录

### 5.6 相声腔语言口径（2026-11-21 二次修订，原「同龄同行」仍适用）

音色气质仍是「同龄同行讲给你听」，但**语言要更放开**：相声的放松感来自语言，不是来自音色。
文本很正式、声音很随意，是最典型的失败。

口播稿文风规则（写进生成提示词，硬负向清单）：

- 用「你」；「您」可以用，但只用于抬杠调侃（"您这个『哟』，值一套架构方案"），**不能用于敬语**
- 禁止「首先 / 其次 / 最后」三件套，改成「先说……然后……」；禁止「综上所述」「总而言之」
- 一句话不超过 20 字，超过就拆——相声没有长句
- **语气词是表演的一部分**，允许并鼓励「哟」「嘿」「得」「您等会儿」，但每个包袱点最多一个
- 符号读法统一（形态无关，必须遵守）：`O(n log n)` 读「O n log n」；`!=` 读「不等于」；`->` 读「变成」；`[]` 读「列表」或「数组」；下划线读「下划线」而不是连读
- 代码不逐行念，改为「这段代码干三件事：先……再……最后……」，最多点名 2 个关键行

7 类情绪的 instruct 写法（CosyVoice2 自然语言指令，作为模板参数）：

| 标签 | instruct 模板 |
|---|---|
| `banter` | 就像跟朋友聊天，随便点儿，语速偏快，别端着 |
| `setup` | 一本正经地下个结论，说得越肯定越好 |
| `deadpan` | 面无表情地回一句，短、平，不要演 |
| `punch` | 抖包袱，前面收着，最后一个字咬住——别喊 |
| `realize` | 突然反应过来，短促地"哟"一声 |
| `contrast` | 前半句轻飘飘，后半句压下来 |
| `wrap` | 收住，放慢，像把话轻轻放桌上 |

**反播音腔的三道闸**：① `emotion_gain` 0.55 起步、上限 0.7（讲解怕朗诵腔要压低，相声要表演性反而要放开）；
② 同一小节内 `punch` 不超过 3 次——包袱多了就不响；③ 保留语气词与不完整句（"啊""哟""您等会儿"），
**混音时不要修掉换气和犹豫**，修干净了就是播音腔。

### 5.7 叙事形态：相声式闲聊（2026-11-21 二次修订）

**基调先定死：轻松、愉快、可以走神。** 这不是「讲解加笑点」，是**泛听**——目的是磨耳朵、
建立熟悉感，不要求记住细节。合格标准只有一条：**擦着碗听、走神两分钟，回来还能接上。**

上一版的「面试回放」被否掉，原因记在这里避免重犯：它有压力、要专注、信息密度高，和磨耳朵正好相反。
它更该当**练习模式**（M3 的交互式演示：先答再看），不该占音频的主线。

#### 相声的三个可迁移结构

| 相声手法 | 技术版落地 | 为什么有效 |
|---|---|---|
| 逗哏装懂 | 用最朴素的直觉讲（"缓存不就是把数据放近点儿嘛"） | 先说出听众的默认认知，认同了才好拆 |
| 捧哏拆台 | 不批评，顺着推，推到矛盾浮现（"那数据改了呢？"） | 认知失调让听众自己发现，比被告知有效 |
| 三翻四抖 | 同一个误解讲三遍，第四遍变奏解开 | **重复＝走神可恢复；变奏＝笑点** |

**笑点只能来自认知反转**，不能硬塞段子。"原来我一直理解反了"是技术相声唯一稳的包袱。
听不懂的梗一律删——它是磨耳朵，不是考听力。

#### 角色设定

| 角色 | 人格 | 说话方式 |
|---|---|---|
| 逗哏 `dou` | 干了三年、自以为门儿清的新人 | 语速快、爱下结论、爱说"这不就是……嘛" |
| 捧哏 `peng` | 干了十年、懒得纠正的老手 | 词短、语气平，只问"那……呢？"；一针见血但不教育人 |

**捧哏不负责讲解**——这是最容易写错的地方。捧哏只干两件事：让逗哏把话说下去、把矛盾逼出来。
一旦捧哏开始解释概念，就变成双人讲课，包袱全没了。

**角色要跨章固定**：40 章用同一对角色与同一对音色（"老张带小李"这种设定），不每章换人。
磨耳朵场景的核心是**熟悉感**——用户听熟这两个声音，下次点开不用重新适应，这是复听率的基础，
也是零成本的角色 IP。

#### 结构模板（替代初版的五拍）

`闲聊开场（banter）→ 一翻：下个错结论（setup）→ 拆台（deadpan）→ 二翻：换个例子说同一个错（setup）
→ 再拆（deadpan）→ 三翻：推到极端（setup）→ 抖（punch）→ 收（wrap）`

每章 12–18 分钟，**每 3–5 分钟埋一个 10 秒小结**（"说白了就是……"）——这是走神后的靠岸点。

**章首必带「上回说到」式回顾**（15 秒内），两个场景都受益：连播时不突兀，断点重听时能接上。
这是评书手法，也是磨耳朵形态里最便宜的一个设计。

#### 风格样例（供评审，非定稿）

> 逗：我跟您说，缓存这事儿特简单，不就是把数据放近点儿嘛。
> 捧：嗯。
> 逗：数据库慢，我搁内存里，一查就有，快得不是一星半点儿。
> 捧：那数据要是改了呢？
> 逗：改了……改了就再放一份新的进去呗。
> 捧：旧的什么时候走啊？
> 逗：旧的……（停）哟。
> 捧：您这个"哟"，值一套架构方案。

#### 单口怎么办

单口相声＝自己跟自己抬杠：先替听众说一句错话（"你可能觉得 X"），再自己拆（"我一开始也这么想"）。
比对口省一个音色，但**笑点密度天然低三分之一**，所以单口只给 A 类概念章用——
概念章的重复本来就是理解机制（同一原理换三个例子），不需要对话来推。

#### 硬约束（写进内容校验，不靠人工约定）

- 逗哏单次发言 ≤5 句（超过就变成讲座了）
- 捧哏每次插话必须推进：带新问题，不能只是"嗯""对""是啊"
- **每 3–5 分钟必须有一个"说白了"小结**，否则判为「走神不可恢复」
- 每章 `punch` ≥2 次、≤6 次（少于 2 笑不起来，多于 6 就油了）
- 两端音色盲听可辨，不得共用参考音频
- 禁止：网络流行语、谐音梗、"听懂掌声"式煽动、贬低任何技术栈

#### 分派规则

| 层级 | 形态 | 依据 |
|---|---|---|
| A · 复杂概念 | 单口（自问自答） | 重复是理解机制，不需要对话来推 |
| B · 常见场景 | 对口（抬杠） | 有过程、有错误做法，天然是逗捧结构 |
| A+B 混合 | 按小节拆：概念小节单口、场景小节对口 | 段落级声明 `narrator` |
| C · 必须看 | 不做音频 | 见 §3.1 |

### 5.8 脚本模型：先微调还是先提示（2026-11-21 新增）

先分清微调能解决什么、不能解决什么。

**训练栈已定（2026-11-21）**：复用用户既有 `llm-finetune-lab`（ms-swift 4.5 + QLoRA 4bit + Qwen3-4B-Instruct-2507，RTX 4070 Laptop 8GB）。
数据构造、训练配置与评估三关见同目录 `FINETUNE-PLAN.md`，执行手册见 `scripts/finetune/README.md`；本节只保留「要不要微调」的决策门。

| 你观察到的症状 | 微调有用吗 | 正确解法 |
|---|---|---|
| 输出 JSON 坏、漏情绪标签 | ❌ | 结构化输出 / schema 约束 + 重试 |
| 术语读法错（`O(n log n)`、`!=`、下划线） | ⚠️ 不必 | **朗读词典后处理**，比训练便宜两个数量级 |
| 文风偶尔跑偏 | ⚠️ 有限 | few-shot 3–5 个黄金样本通常就够 |
| 每章都要重写同样的开场 / 小结，改得累 | ✅ 有价值 | 这才是微调真正解决的问题：**风格复现的稳定性** |
| 系统性重复同一个毛病（AI 腔、爱用"首先其次"） | ✅ 有价值 | 微调 + 负向样本对照 |

**决策门（M2 结束时用数据判定，不靠感觉）**：

- 若人工修改率 **>35%**，且 **top3 问题类型占修改量 60% 以上**（说明是系统性偏差而非随机噪声）→ 微调划算
- 若修改率 **<20%**，或问题分散 → 微调是过度工程，继续打磨提示词与词典

**若触发微调，方案轮廓**：

- 基座：7B 级指令模型，**与业务主档模型不同源**，避免污染线上推理；走 LoRA（r=8–16），不碰基座权重
- 数据：M1 的 3 章人工黄金稿各扩 3 个变体 + 人工优选 + **负向样本**（"这样写不行"的对照），约 60–100 条；混入 20% 通用指令数据防灾难性遗忘
- 训练：本机单卡 1–2 epoch（与 §7.1 的 GPU 决策一致）
- 评估：留 5 章盲测，只看两个指标——人工修改率、3 人盲听评分；不看困惑度
- **定位：离线生产工具**。只在制作期跑，不进产品、不进容器、不产生运行期出网，符合 C1 / C4

**风险要提前说**：40 章约 6 万字的样本量偏小，微调后很可能只学会"这三章的味道"，泛化到 C 类或新章反而更差；评估成本（人工盲听 + 修改统计）往往高于收益。所以**M1 阶段明确不微调**——先人工写出 3 章黄金样本，让"什么算好的口播稿"变成可对照的标准，再谈让模型学它。

**可选的并行试验（不阻塞主线）**：如果仍想早点验证微调值不值，M1 期间可以跑一个最小规模的 LoRA 试验——20–30 条数据、单卡几十分钟，只回答一个问题：**微调组的输出是否明显比 few-shot 组更像人话**。若两组盲测无差异，M2 就不必再投入；若有明显差异，再按上面的方案扩数据。用最小成本先证伪，比直接铺 90 条数据稳妥。
