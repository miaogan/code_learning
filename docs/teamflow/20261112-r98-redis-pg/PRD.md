# r98 引入 PostgreSQL 与 Redis

## 背景

r97 完成公网入口（TLS、生产守卫、证书与备份脚本）后，剩下的短板全在**数据层**：

- **SQLite 是单文件单写锁**：`busy_timeout` 只是缓解重试，多副本部署在物理上不可能，
  而公网产品的下一个必然动作就是「多开一份」；
- **限流与熔断是进程内内存**（`deque` + `monotonic`）：N 个副本各放 N 倍流量，
  压测单副本永远看不出，这是最容易骗过自己的形态；
- **全文检索依赖 FTS5 编译期能力**：环境没编进去就静默降级成 `LIKE`，线上与本地行为不一致；
- **备份靠拷页面**：`Connection.backup` 可用但只支持整库，排障时无法只回滚一张表。

## 目标

1. PostgreSQL 成为**唯一**数据源，SQLite 路径整体下线（不做双后端兼容）；
2. Redis 承担四类「多副本必须共享、丢了能重建」的职责：限流窗口、会话缓存、
   业务读缓存、分布式锁；
3. 现有 SQLite 数据可一次性迁入 PG，幂等、可重跑、带行数校验；
4. 测试基座跟着换，且**不降低**隔离强度。

## 非目标

- 不引入 ORM 或迁移框架（保持 `CREATE TABLE IF NOT EXISTS` + `ADD COLUMN IF NOT EXISTS`）；
- 不做读写分离、分库分表、PG 高可用集群；
- 不做 Redis 集群 / Sentinel（单实例 + 降级足够当前规模）；
- 不改任何业务语义（报告、画像、计划的字段与判定口径逐字不变）。

## 关键设计决策

### 1. 用适配层翻译占位符，而不是改 149 处 SQL

`repository.py` 有 149 处 `?` 占位符。逐行改成 `%s` 的风险是「改漏一处，运行期才炸」；
集中在一个 `to_pg_sql()` 里翻译，只有一处需要测。

**陷阱**：psycopg 用 `%` 解析参数，而检索 SQL 里有 `LIKE '%kw%'`，不转义会报
`there is no parameter $kw`。所以必须**先**把 `?` 换成哨兵、**再**把 `%` 转义成 `%%`、
**最后**把哨兵换成 `%s`——顺序反了会把占位符变成字面量 `%%s`。

**另一个陷阱**：无参数 `execute()` 走 simple protocol，不做 `%` 解析。此时若也转义，
`%%` 会原样写进 SQL。所以只在带参数时翻译。

### 2. FTS5 → `pg_trgm`，而不是 `tsvector`

`to_tsvector('simple', …)` 把连续中文当成一个词，「闭包」检索不到「闭包是什么」；
`zhparser` 需要额外编译扩展。trigram 对中英文子串都有效，且与原有 `LIKE` 降级路径
**返回结果完全一致**——这是一次「只变快、不变语义」的替换，`mode` 恒为 `like`，
前端不会再看到「未启用全文索引」的提示。

`CREATE EXTENSION` 需要超级用户，托管 PG 常见不给：失败只记 WARNING 并跳过 GIN 索引，
检索退化为顺序扫描，功能不受影响。

### 3. 熔断的在飞计数保持进程内，只共享错误率

「全局在飞请求上限」如果跨副本共享，10 个副本共用一个 32 的上限，等于每副本只能用 3 个——
那是错的：在飞数是**单副本的并发**，本来就该各自算。

Redis 共享的是**错误率样本**（所有副本看到同一个下游故障率），这样 AI 服务大面积故障时
所有副本同时打开熔断，而不是各自攒够 `BREAKER_MIN_REQUESTS` 才开。限流窗口则完全共享。

### 4. 测试从「每例一个 SQLite 文件」改为「共享 PG + 每例 TRUNCATE」

建 27 张表约 80ms，乘 1700 例是两分多钟；`TRUNCATE … RESTART IDENTITY CASCADE` 约 5ms。
表结构由会话级 fixture 建一次。

代价是**失去了「文件不存在」这个天然隔离**，所以补了三个专用库：
`sc_test_empty`（验证未初始化路径）、`sc_test_legacy`（按旧版 DDL 造表验证补列）、
`sc_test_seed`（模块级共用已灌种的库，避免重复导入 1164 题）。

### 5. Redis 故障一律降级，不返回 503

Redis 是加速与跨副本一致层，真值都在 PG。它挂了的正确表现是「限流精度下降、缓存不命中」，
而不是「全站不可用」。所有调用点捕获异常后走兜底分支，并在 30 秒内不再重试（避免每次请求
都撞一次 socket 超时）。

## 验收标准

| 编号 | 标准 | 验证方式 |
|---|---|---|
| AC-1 | 27 张表在 PG 上全部建成，无 SQLite 语法残留 | `init_db()` 后查 `pg_tables` |
| AC-2 | `init_db()` 幂等：第二次执行结构逐字不变 | `_schema_snapshot()` 比对 |
| AC-3 | 占位符与 `%` 转义正确，含 `LIKE` 的检索可用 | 检索用例 + 单元测试 |
| AC-4 | 题库检索结果与 SQLite LIKE 分支一致 | `test_r51_eval_harness` |
| AC-5 | 存量库（缺列）跑 `init_db()` 自动补列且不重导数据 | `test_r11_data_layer` |
| AC-6 | 限流窗口跨进程共享，超限返回合理重试秒数 | `test_r98_redis`（真实 Redis） |
| AC-7 | 会话缓存命中不打库，登出即刻失效 | 删行后仍可读 + 登出后读不到 |
| AC-8 | 读缓存按前缀失效，`latest` 与按 id 同时清 | `test_r98_redis` |
| AC-9 | 分布式锁互斥、异常也释放 | `test_r98_redis` |
| AC-10 | Redis 未配 / 不可达时全部降级不抛错 | `test_r98_redis` 降级用例 |
| AC-11 | 生产档无 `REDIS_URL` 拒绝启动 | `test_r97_production_guard` |
| AC-12 | 迁移脚本幂等、逐表行数校验、复位自增序列 | `--dry-run` + 实跑 |
| AC-13 | 全量后端测试通过、ruff 全绿 | `pytest -q` / `ruff check` |
