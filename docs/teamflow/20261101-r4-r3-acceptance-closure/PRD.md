# PRD · r3 验收遗留项闭合（R-1 / D-2 / D-3 / D-4）

## 1. 背景与目标

r3（`docs/teamflow/20261031-r3-memory-resume-polish/`）判定为「⚠️ 有条件通过」：15 条 AC 全部有执行证据，但留下 1 条阻塞项（R-1）与 3 条可随下轮清理的瑕疵（D-2/D-3/D-4）。实现代码已由 host 补提交（commit `611643d`），工作树干净，分支 `feat/dev-skill-coach`。

**本轮唯一目的**：把「有条件通过」闭合为「通过」。不做任何新功能，只修这 4 条，修完重跑受影响门禁。

**已实测的当前基线**（本轮以此为回归基线，不得退步）：

- `backend/`：`python -m pytest -q` → 113 passed
- `frontend/`：`npm run typecheck` → 0 error；`npm run lint` → 0 error / 28 warning；`npm test` → 7 passed；`npm run build` → ✓ built

**四条的实质问题**：

1. **R-1（本轮唯一阻塞项）** 润色页右栏「原版」Tab 显示的是**被改写句子的 `original_text` 按 `\n\n` 拼接**（`frontend/src/pages/PolishPage.tsx` 的 `buildOriginal`），而 Tab meta 写着「原版 · 逐字取自简历正文」，DESIGN（r3 `DESIGN.md` §240）约定「`原版` = 简历正文（只读、`--bg-inset`、可滚动）」。后果：用户拿到的是「只有被建议过的那几句」，**无法核对「没有被建议的段落是否还在成稿里」** —— 这恰好是润色功能最需要用户确认的事。按设计补齐真实正文（不采用「降级设计/改文案」那条路）。
2. **D-2** 导出文件名写死 `简历润色-<yyyy-mm-dd>.md`；DESIGN §284 约定 `简历润色-<原文件名>.md`。根因在**读路径契约缺文件名**（`documents.file_name` 上传时已落库，但润色响应没带出来）。
3. **D-3** `backend/app/services/profile_merge.py` 的 `CONTRACT_READY=False` 分支（`_FallbackEvidence` / `MergedSkill` / `MergedProject` / `MergedProfile`）在契约落地后已成死代码，与 `app/schemas.py` 形成双份模型定义（双源漂移风险）。
4. **D-4** 画像页合并摘要条缺 DESIGN 要求的「查看历史能力项」按钮（§46 / §191）；历史能力项目前只藏在页内下方折叠分组里，入口可达性不达设计。

**目标（可判定的完成态）**：用户在润色页打开「原版」Tab 能读到**整篇简历正文**并核对其与润色版差异；导出文件名是**自己的简历文件名**；画像页合并摘要条**一键到达历史能力项**；`profile_merge` 只剩一条模型来源；全部门禁不低于基线。

## 3. 范围与非目标

**范围内（只此 4 条 + 它们必需的契约与断言）**

- R-1：契约补 `resume_text` 并在前端用它渲染「原版」Tab（含删除 `buildOriginal`）。
- D-2：契约补 `file_name` 并让导出文件名用它（含无文件名回退与字符清洗）。
- D-3：删除 `profile_merge.py` 的 `CONTRACT_READY=False` 分支与四个双份模型。
- D-4：合并摘要条补「查看历史能力项」按钮 + 折叠分组联动与可达性。
- 上述改动必需的契约双侧同步、后端/前端断言、受影响门禁复跑与验收证据留痕。

**非目标（本轮明确不做）**

- 不做远程历史记忆注入提示词、不做跨会话持久化（沿用 r3 决定）。
- 不做存量数据回填：旧 `documents` 行若无文件名，走回退格式（不猜、不补）。
- 不重构 4 条之外的文件；不顺手统一代码风格；不动 r3 已通过的契约字段语义。

## 4. 反面目标（anti-goals）

> 即使测试全绿、这 4 条「看起来都做了」，下面任一情形发生，用户仍会判定本轮失败。

1. **「原版」Tab 塞进 3 屏正文后，右栏滚动区和页面滚动打架**：用户滚右栏滚不动、或页面被正文拉长导致左栏建议卡被顶走 —— 表现是「原版能看，但建议我看不见了」。判定点：正文 1 屏与 5 屏两种简历下，左栏首条建议卡的屏幕位置不变，右栏容器内独立滚动。
2. **看着对、导出漏**：原版 Tab 显示整篇正文，但导出仍走旧拼接/旧文件名 —— 用户核对时以为段落都在，导出打开发现未改写的段落没了，或文件名还是日期。判定点：同一次会话内「原版文本 ⊇ 原文全部段落」与「导出文件内容 == `full.markdown` 且文件名含原简历名」两条同时成立。
3. **文件名修好反而更糟**：把 `a/b.pdf`、带 `:` 或 `?` 的 macOS 导出名硬塞进下载名，浏览器静默截断成 `简历润色-.md` 或触发保存路径异常，用户拿到的文件比旧格式更难认。判定点：用 4 组脏文件名（含路径分隔符、非法字符、超长名、空名）各导出一次，全部落地为可读的 `.md` 且不报错。
4. **D-4 是「有按钮没内容」**：点「查看历史能力项」后什么都没发生（分组仍是折叠态、或滚到位置但内容还在折叠里、或历史项为 0 时按钮照样可点无反馈）。判定点：历史能力 ≥1 项时点击一次 → 展开态可见且焦点在分组；0 项时按钮不存在。
5. **删死代码顺手把画像改坏**：`profile_merge` 精简后证据链少一条或 `historical` 隔离失效，pytest 仍绿但画像页「历史能力」分组变空 —— 技术上通过、产品上溯源断裂。判定点：删除前后用同一份二次合并数据，画像页证据条数与 `historical` 条数一致。

## 5. 交互流程摘要

**润色页（R-1 + D-2）**

1. 进入 `/polish` → 有简历有画像 → 点「开始分析」→ 生成逐条建议（左栏）。
2. 右栏 Tab：`[原版][润色版]`。**原版 = 整篇简历正文**（只读、`--bg-inset` 底、容器内可滚动，含未被建议的段落）；**润色版 = 采纳/忽略即时反映的成稿预览**（服务端 `markdown` 单源）。
3. 采纳/忽略只动预览，不写 `documents.text`、不跨会话持久化（r3 口径不变）。
4. 点「生成成稿」→ 取 `POST /polish/full` 的 `markdown`；导出按钮以 `<原文件名>.md` 命名保存该 markdown 原文（裸传）。

**画像页（D-4）**

1. 上传 → 生成/合并画像 → 顶部合并摘要条：`本次合并 · 新增 N 项能力 · M 项转为历史 · 证据 +K` **[查看历史能力项]**。
2. 点该按钮 → 页面滚到「历史能力」分组 → 分组自动展开（`▾ 历史能力 X 项（本次简历未出现 · 不参与出题与诊断）`内容可见）→ 焦点落分组容器；此后可继续用既有折叠 chip 自行收起。
3. 历史能力 0 项 → 不渲染该按钮（避免死点击）。

**契约读路径（R-1 + D-2 共用一处改动）**

- `POST /api/resumes/{resume_id}/polish` 响应内新增 `resume_text`（整篇正文）与 `file_name`（原始文件名），**不新增路由**：错误码闭集、错误 envelope、既有 16 端点 OpenAPI 面保持不变。
