# PRD · 长期记忆（成长时间线 + 增量画像）与简历 AI 润色

## 1. 背景与目标

现状（0.1.0 + r2 已交付）：四步闭环可用，但每一次上传简历都会生成一份新画像（`latest_profile` 取 `updated_at` 最新一行），测评能力只存在于历史表格里，**系统没有"记忆"**：用户看不到自己从哪里来、什么变好了、什么短板复现；简历本身也只有"读"，没有"改"。

用户诉求（原始原话）：*希望有类似于长期记忆的机制，累计用户的信息、记录用户的成长；并且增加对简历的 AI 润色功能。*

目标（可衡量）：

- **G1 有记忆**：任何一次"完成面试 / 完成笔试 / 上传简历并画像成功"，都在成长时间线留下 1 条事件，且事件里的分数与既有页面显示的分数一致（差 ≤0.05）。
- **G2 可对比**：同一类型相邻两次事件之间，用户能看到分数 delta 与"短板复现 / 消失"，不需要自己心算。
- **G3 画像不丢历史**：同一能力项在多次简历里出现时证据累积（≥2 条可溯源原文），消失的能力项变成"历史"而不是消失，Active 集合只反映最新简历。
- **G4 简历可改**：对简历项目 / 经历给出「原句 → 建议句 → 为什么这么改」，可逐条采纳 / 忽略；可一键生成全篇润色版并导出 .md；改写基准是画像目标岗位且可临时指定。
- **G5 可复用**：润色建议生成收敛为一个 service，诊断报告后续可直接复用（本轮不接报告 UI）。

本轮的明确排除：**不把历史记忆注入 AI 提示词**（用户已明确选择不注入；出题与评分仍以当前画像为准）。

## 2. 用户故事与验收标准

> 验证方式图例：`本机可验` = 沙箱内可执行（pytest / typecheck / lint / 无浏览器的静态与逻辑检查器）；`需复跑` = 本沙箱 spawn EPERM 或需视觉判断，须开发机 / CI / 人工复跑。

| AC-5 | **本次 vs 上次对比**：对比对象 = 同类型的上一条完成事件；展示面试均分 / 笔试总分 delta（带符号、保留 1 位小数）与短板复现 / 消失清单；无同类上一条时显示"首次测评，暂无对比"（不得输出 0.0 分差、不得出现 NaN / undefined）。对比数值由服务端随事件返回（`comparison` 字段），前端不得自行做减法或再拼接 | P0 | 本机可验（pytest 三例：有上一条 / 无上一条 / 上一条是另一类型）；需复跑（视觉） |

## 3. 范围与非目标

**范围内**：成长时间线（事件写入 / 读取 / 页面 / 同类对比）；画像增量合并（证据累积、历史项保留、归一、隔离）；简历润色（逐条建议、反幻觉校验、采纳/忽略、一键成稿、导出 .md、目标岗位重跑）；润色 service 边界；门禁与检查器。

**非目标（本轮不做）**：
1. 不把历史记忆注入 AI 提示词（明确排除；出题与评分仍以当前画像为准）。
2. 不做画像版本管理 / 版本回滚 / 版本间 diff 编辑器（只保留"当前合并画像 + 历史项标记"）。
3. 不做多份简历并存切换的画像（画像恒为单一当前合并画像；润色按 `resume_id` 可针对任意历史正文）。
4. 不接入诊断报告 UI 的"简历改进要点"（只保证 service 可复用，接线留后续轮次）。
5. 不做采纳状态的跨会话持久化、不做"润色后再上传"闭环、不做 ATS 打分 / 翻译 / 自动投递。
6. 不做时间线的人工编辑 / 删除 / 备注；不做时间线导出。
7. 不重做既有四步闭环、报告、历史页布局（只在历史页新增时间线区）。

## 4. anti-goals / 反面目标

> 以下每一条都是"测试全绿、但用户会当场否掉"的失败形态，均可被使用者直接观察到。

1. **旧证据被顶掉**：上传第二份简历后，画像里每项能力只剩 1 条 `source_quote`，用户点开溯源只能看到最新那份简历——"长期记忆"变成"只有最近一次"，用户无法确认这条能力是从哪份简历来的。
2. **记忆里的数字对不上**：时间线说上次面试 7.4、历史页说 7.8、报告说 7.2；或事件在失败 / 重复提交后出现两条、甚至出现一条"失败测评"的记录——用户一旦发现记错，整块记忆都不再可信。
3. **系统忘不掉旧简历**：换了一份不含某技能的新简历后，出题与诊断仍反复把该项当短板考，用户感觉"它在拿旧简历坑我"，于是不敢再上传新简历。
4. **润色编造事实**：建议句里冒出原简历没有的"2023 年 GMV 8000 万""某大厂""主导 30 人团队"，用户不敢用、也无法验证——一次幻觉就让这个功能失去信任（这也是 AC-9 后置校验的理由）。
5. **成稿看起来像别人的简历**：一键成稿把整段经历重写成另一种叙事，用户认不出自己的工作，或把"忽略"的建议也塞进成稿；导出的 .md 与页面显示不一致（比页面上多/少条目）。
6. **等待没有尽头**：点"一键生成全篇润色版"后 30 秒以上只有转圈、没有任何进度或可读提示，用户不知道是卡死还是仍在跑，只能刷新——刷新又丢掉刚采纳的条目。

## 5. 交互流程摘要

1. **上传 → 合并**：`/upload` 上传简历 → 解析 → 画像生成改为"与当前画像合并" → 成功后跳画像页；画像页顶部显示本次合并摘要（"新增 2 项能力 · 1 项转为历史 · 证据 +3"），能力项内可展开多条溯源原文（旧 / 新，带来源简历文件名与时间）。
2. **测评 → 记忆**：面试逐题答完 / 笔试提交成功后，后端写 1 条事件（同步返回给前端即可，不阻塞跳转）；事件写入失败不得阻止页面进入报告流程，但必须在历史页可见"该次未记录"的说明（不静默）。
3. **历史页**：既有趋势表下方新增「成长时间线」，每条可展开"本次 vs 上次"对比卡（分数 delta + 短板复现 / 消失）。空态引导去做一次测评。
4. **画像页 / 报告页 → 润色**：新增路由 `/polish`（侧栏「简历润色」），从画像页摘要按钮与报告页底部入口进入；默认 `target_role` = 画像目标岗位，可临时改写并重跑。
5. **润色页**：左侧条目列表（逐条卡：原句 → 建议句 → 理由 → 采纳 / 忽略），右侧成稿区（Tab 切换原版 / 润色版）→「一键生成全篇润色版」→ 导出 .md。任何 AI 失败都在对应区块内出现 `InlineError`（中文原因 + 重试），页面其余区块保持可用。

## 7. 依赖与风险

- **依赖**：既有 `services/history.py`、`services/diagnosis.py`、`services/profile.py`（含 `verify_quotes`）、`services/ai.py`（`complete_model` + `AI_TIMEOUT_S`）、`repository.py`（唯一 SQL 出口）；r2 的反馈约定（Toast 成功 / InlineError 失败）与报告文本单源。
- **R1 契约破坏**：`ProfileSkill.source_quote` → 证据列表是批量字段变更；缓解：保留 `source_quote`（取首条证据）作为兼容字段，新增 `source_quotes[]` 与 `status`，两侧同步改；存量 payload 缺字段时读取兜底（`status` 缺省 active、`source_quotes` 回填 `[source_quote]`），不做迁移框架并在 `memory.md` 记一次性说明。
- **R2 合并判定歧义**：同一能力项判定靠归一规则，误合并会抹掉区别；缓解：归一规则写成表驱动单测（含全角 / 空白 / 大小写 / 中英混写），只归一无歧义的形态，模糊近义项不自动合并。
- **R3 历史项隔离过狠**：active 项变少 → 出题素材不足、诊断变浅；缓解：active <3 时以 `tech_stack` 补齐并在页面提示"能力项不足，本次出题使用技术栈兜底"。
- **R4 长耗时 AI**：整篇成稿可能需要多次模型调用，超过 20s 超时；缓解：建议批量单次返回 + 成稿复用已生成建议（不再重复调模型），失败可重试且不落半成品；若需提高超时，走 `AI_TIMEOUT_S` 配置并写进技术方案。
- **R5 幻觉校验的边界**：校验器只能拦截"数字 / 专名新增"，拦不住语义跑偏；缓解：UI 明示"AI 建议，请核对后使用"，并在建议卡保留原句以便对比；验收保留人工抽检。
- **R6 沙箱限制**：`vitest` / `vite build` spawn EPERM，视觉 / 动效 / 真机下载粘贴需开发机复跑；静态检查器可覆盖逻辑与源码断言，但覆盖不到真实渲染与动画。
- **R7 单用户本地并发**：两个上传同时到达时合并可能交错；缓解：合并为"读—合并—写"的串行化路径（同一库上互斥 + 以 `updated_at` 乐观校验），失败重试一次。

## 10. 假设与待澄清

- **Q1（taste）时间线放哪**：历史页内嵌一个「成长时间线」区（推荐：导航仍 6 条不变、与既有趋势表天然相邻）与新增独立「成长」路由各有利弊；若选独立路由，历史页只留趋势表、侧栏增至 7 项，AC-4 的落点随之改变。
- **Q2（taste）原版 / 润色版怎么摆**：Tab 切换（推荐：窄屏可用、单栏阅读更专注）vs 并排双栏（1440 下每栏约 600px，长句阅读与行宽都更差）；若选并排，AC-11 的布局断言与截图口径要一起改。
- **Q3（taste）改写强度**：保守润色（推荐：只改措辞与结构，不改事实与数字，缺数值处写 `〈待补充〉` 留用户填）vs 激进重写（允许按 STAR 结构重排、可建议补充占位句）。这直接决定 AC-9 的降级策略与用户对"这是我的简历"的认同。
- **Q4（taste）重复上传同一份文件**：每次上传都记 1 条事件（推荐：忠于"每次上传新简历"原话，但事件标 `duplicate: true`、页面弱化显示）vs 短期内同文件去重（不记事件也不合并）。选后者会改变 AC-1/AC-3 的计数口径。
- **Q5（taste）整篇润色的等待形态**：先看逐条建议、再点"生成成稿"（推荐：可先审阅、失败只重试成稿这一步，对应 anti-goal 6）vs 一键直达、单次等待（简单但 30s 只能转圈）。选后者需要额外定"多久算超时"。
- **Q6（fact）存量数据是否回填时间线**：本机现有 `backend/app.db` 是否已有历史简历 / 测评数据，我无法从仓库判断；假设**不回填**（时间线从本版本上线后的新事件记起，页面空态注明"历史数据从本版本起记录"）。若你要回填，需要一次性脚本把既有 `runs` / `documents` 转成事件，AC-1 的口径随之扩展为"包含存量数据"。
