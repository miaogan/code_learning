# r33：上传页失败提示 —— 200 不等于成功，旧失败也不该常驻

## 问题与排查

用户反馈：「上传简历流程，后台接口只有 200，但怎么还是失败」。

真实环境复验（真后端 + Playwright + 逐条记录 /api 响应 body）：

- **正常路径**：`POST /api/resumes` 200 → `POST /api/resumes/{id}/profile/async` 200 →
  `GET /api/profile-jobs/{id}` 轮询两次 200（running → completed）→ 页面进完成态。无异常。
- **复现成功**：一个「failed」的 latest 任务在页面挂红条，而该次请求链路全是 200。

### 结论一：异步任务接口的 200 是「查询成功」，不是「生成成功」

`profile_jobs` 相关端点的语义：HTTP 200 只表示任务受理 / 状态查询成功；
真正结果在 **body 的 `status`**（running / completed / failed），失败原因在 `body.error`。
所以「接口全 200 但 UI 报失败」在设计上完全可能：那是后台任务业务失败。

### 结论二（真 bug）：failed 提示没有时效，会永久常驻

r32 加的「最近一次任务 failed 就明示」只判断状态不看时间：一条历史失败会挂在
**每一次**打开上传页，用户升级 App 后看到的就是「接口全 200 却总说失败、而且怎么点都还在」。

### 结论三（数据层面）：开发库被 r32 的测试脚本污染

上一轮截图脚本为造失败场景，直接改写过 `profile_jobs` 行；这些行恢复为真实终态
（completed），并在本轮验证后清掉全部人造行。

## 修复

- `lib/profileJob.ts`
  - `shouldSurfaceFailure(job, nowMs)` 增加 **24 小时时效窗口**：窗口内的 failed 如实提示，
    窗口外不再打扰（用户早已不再等那一次结果）；`created_at` 缺失/不可解析时仍提示（可见性优先）。
  - `jobFailureMessage` → `jobFailureNotice`：文案改为
    「简历已上传成功，但画像生成失败：<后端中文原因>」——先把「上传/解析已完成」说清，
    再给失败原因，避免用户误以为上传接口挂了（这正是「200 为什么失败」的认知缺口）。
- `UploadPage`：轮询终态与重接入两处均改用 `jobFailureNotice`。

## 验证

- 真实浏览器三情形：
  1. 新鲜 failed 任务 → 红条「简历已上传成功，但画像生成失败：AI 服务响应超时，请稍后重试」+ 重试 + 先去画像页
  2. 2 天前的 failed 任务 → 页面无任何红条（旧失败不再常驻）
  3. 真实 docx 上传全链路 → 200/200/200/200 走通，4 秒完成并进「查看画像」完成态
- 前端 typecheck / lint 0 warning / **204 测试**（新增时效边界、文案用例）/ build 全绿。

## 经验

- 异步任务型接口必须在产品文案里把「HTTP 成功 ≠ 业务成功」讲清楚，否则用户只会在
  网络面板里数 200。
- 「必须可见」类提示一定要有时效或消亡条件，否则正确性修复会变成噪声。
