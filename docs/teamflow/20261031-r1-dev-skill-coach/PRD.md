# PRD · 开发者能力提升教练（dev-skill-coach）

基线依赖：无

## 1. 背景与目标

**背景**：开发者普遍"想提升但不知道该补什么"，刷题平台与课程平台彼此割裂：既没有围绕个人经历建立的画像，也不给"你弱在哪"的证据，学完仍不知道下一步。

**目标**：以简历为唯一输入建立可追溯到原文的用户画像，用模拟面试与笔试产出**带证据的短板清单**，再用诊断报告把短板接到精选基础课程，形成首版最小可用闭环。

**首版成功标准**：一名新用户在一次会话内 5 分钟内走完"上传简历 → 面试或笔试 → 拿到诊断报告 → 点开至少一门推荐课程"；每条短板都能指回具体题目与得分。

## 2. 用户故事与验收标准

- **US-1** 作为求职中的开发者，我上传简历后想看到系统对我的画像，确认它"真的读懂了简历"。
- **US-2** 作为不知道深浅的开发者，我想先做一场模拟面试/笔试，拿到每道题的得分和点评。
- **US-3** 作为准备补课的开发者，我想拿到按优先级排序的短板清单，每条都有证据，而不是只有一句"基础薄弱"。
- **US-4** 作为想立刻行动的开发者，我想在短板旁边直接看到该学哪门基础课，点开就能学。
- **US-5** 作为复用的用户，我刷新页面后不想重走一遍流程。

## 3. 范围与非目标（首版）

**范围内**：React 前端 + Python FastAPI 后端的 Web 应用；简历上传解析 → 画像 → 模拟面试（文本作答）→ 模拟笔试（客观题自动判分）→ 短板诊断报告 → 精选课程清单与外链跳转；本地 SQLite 持久化；服务端统一调用模型 API。

**非目标（本次不做）**：复杂多租户账号与权限体系；题库管理后台与题库规模化；付费、结算、社区、排行榜；课程内容生产与视频托管（仅清单 + 外链）；扫描件 OCR；移动端原生 App；实时语音面试；代码题自动执行判分（首版笔试题限定为客观题 + 文本题人工评分）。

## 4. 反面目标 / anti-goals

以下不是"没做的功能"，而是**即使测试全绿、用户仍会判定这个产品失败**的具体情形：

1. **画像出现"无源之词"**：画像里列出用户从未掌握的技能（如 Kubernetes），且 `sourceQuote` 为空或与简历原文对不上 —— 用户一眼判定"这不是我"，信任当场归零。
2. **题目与简历脱节**：上传的是前端简历，考卷却是分布式事务与竞赛算法，用户判定系统根本没读简历。
3. **短板无证据**：报告只写"你基础薄弱、多练练"，列不出对应题目与得分，用户无法判断该不该信，也无法自证。
4. **推荐链断掉**：点开推荐课程出现 404、跳到与短板无关的首页，或某条高优先级短板没有任何对应课程 —— 四步闭环在最后一步断掉，等于全流程白跑。
5. **密钥可被看见**：浏览器 DevTools、网络请求或打包产物中能直接看到模型 API Key / 可从浏览器直连模型供应商。

## 5. 交互流程摘要

1. **上传**：首页上传简历（格式/体积校验）→ 进度提示 → 解析成功展示正文摘要。
2. **画像**：右侧/下方生成画像卡片（技能标签、技术栈、年限、项目、目标岗位），每条可展开查看 `sourceQuote`，可手工增删。
3. **测评**：可自由选择"模拟笔试"或"模拟面试"；笔试逐题作答并提交判分，面试逐题单屏作答并即时出分与点评。
4. **诊断**：测评结束进入诊断报告页，短板按严重度排序，每条带证据链接（点击回看该题）。
5. **课程**：每条短板下方列出推荐课程卡片与外链；空态提示"多做一题可提高诊断精度"。
6. **历史**：画像与测评记录本地持久化，刷新后可直接回到最新报告。

## 6. 优先级

- **P0（首版必须）**：AC-1 ~ AC-8 —— 构成可跑通的最小闭环与安全底线。
- **P1（紧随其后）**：AC-9 报告导出、AC-10 历史对比。
- **P2（后续迭代）**：题量扩容与题库管理、代码题自动判分、账号体系与云端同步、学习计划与进度追踪。

## 7. 依赖与风险

| 项 | 说明 | 缓解 |
| --- | --- | --- |
| 模型 API | 需可用的 OpenAI 兼容接口与额度，服务端环境变量注入 | `.env` + `.env.example`；无 key 时页面给出明确中文提示而非 500 |
| 解析库 | PDF 文本层依赖 `pypdf`，DOCX 依赖 `python-docx` | 抽取失败降级为"粘贴文本"输入入口 |
| AI 输出稳定性 | 画像/题目/报告为 JSON 结构，模型可能返回非法结构或跑偏 | 服务端 schema 校验 + 一次重试 + 失败可读提示 |
| 外部课程链接 | 第三方链接可能失效 | 清单集中在服务端单一 JSON 文件，便于集中更换 |
| 成本 | 每轮测评多题、多报告调用 | 限制单会话生成次数、缓存画像与题目 |
| 安全 | 首版本地单用户，无鉴权 | 仅本地/内网部署说明；密钥仅服务端 |

## 8. 里程碑建议

- **M5 闭环验收**：刷新持久化、全流程 5 分钟演练、安全核查（AC-7，P1 项随后）。

## 10. 假设与待澄清

**（a）事实类（待你确认的未定事实）**

- **模型供应商与额度**：假设使用任意 OpenAI 兼容接口（`base_url` + `key` 走服务端 `.env`），默认 `gpt-4o-mini` 级模型。若你已有指定供应商或私有模型，会影响默认模型与并发限制。
- **课程清单来源与授权**：假设人工维护 25 门左右的精选清单，外链指向官方文档/公开课，不抓取付费或需登录内容。若要做站内课程页或指定平台，需重写课程模块。
- **PDF 扫描件**：假设只解析文本层 PDF，扫描件提示"请上传文本版"，不做 OCR。若目标用户多为扫描件简历，需引入 OCR 并延长解析时限。
- **题库规模与 AI 生成边界**：假设内置约 80 道种子题（前端/后端/算法/基础各约 20 道）+ 按画像 AI 补题。若要求全部由种子题出卷（可重复、可对比），AI 只用于评分与点评。
- **数据存储**：假设本地 SQLite 单库，无需部署外部数据库。若要云端多端同步，需改成服务端数据库 + 上传用户标识。
- **历史保留量**：假设保留最近 20 次测评，不做清理界面。

**（b）品味类（需要你选的偏好，我给推荐默认）**

- **视觉风格**：默认**深色技术感**（深灰底 + 单一强调色，分数/代码用等宽字体）；理由：目标用户是开发者、单次测评时长较长。若你偏好浅色清爽或偏"招聘产品"风格，需重做配色与组件基调。
- **面试交互形态**：默认**逐题单屏卡片、一题一提交**；理由：单题评分、重试与证据回看更清晰，也避免长对话上下文膨胀。若你更想要连续对话式面试，评分粒度与页面结构都要改。
- **模拟题与简历的贴合度（对应 anti-goal 2）**：默认**贴合为主、允许 ≤20% 的"挑战题"（标注难度）**；若你希望 100% 不出超纲题，会牺牲一部分"发现未知短板"的价值。
- **诊断报告的严格度与语气（对应 anti-goal 3）**：默认**直接但建设性**——短板最多 5 条，每条必须配 1 条可执行动作；若你希望更严厉/更鼓励，文案与排序权重（严重度算法）需调整。
- **测评顺序**：默认**自由选择**，空态引导"先笔试测基础，再面试测深度"；若要求强制顺序（先笔试后解锁面试），流程门禁需改造。
