# r116 画像溯源校验：「同一份简历有时成功有时失败」

- 起始：2026-11-17
- 触发：用户报「上传简历后会出现失败的概率，说是结论在原文中没有体现，这是为啥」。
- 结论：不是模型质量抖动，是**两个设计缺陷叠加**。①`verify_quotes` 要求「全部条目一次性命中」，
  失败率随条目数指数放大（15 条 × 单条 5% ⇒ 只剩 46% 成功率）；②命中判定只去空白，
  把 PDF 抽取留下的不可见字符与全半角差异当成编造。而设计文档里写的「命中失败 → `ai.py` 已重试 1 次」
  **在代码里从来没有发生过** —— 重试只覆盖 JSON / 契约校验，溯源校验跑在那之后。

## 1. 现象能对上的关键特征

用户的原话是「**会出现失败的概率**」，不是「一直失败」。这个「概率」是破案的抓手：

- 如果简历正文抽不出来 → 每次必失败（`EMPTY_FILE`），不会有概率性；
- 如果模型整份在编 → 每次必失败，也不会有概率性；
- 只有「**部分条目踩雷、部分条目合规**」，才会表现为同一份简历反复上传时好时坏。

顺着这条线查到两个独立的放大器，它们乘在一起正好解释「概率」。

## 2. 根因一：一条不合格 → 整份 502（把单条失败率放大成整份失败率）

`profile.py` 原本的语义是「任一条 `source_quote` 不能在正文里逐字命中 → 抛 `AI_SCHEMA_INVALID`(502)」。
这个语义本身没错（anti-goal 1 要求不落「无源之词」），但它把**单条**失败率直接乘成**整份**失败率：

```
P(整份成功) = (1 - p)^N        p = 单条被改写的概率，N = skills + projects 条目数
```

实测标定（`p` 取 2% / 5% / 10%，这是真实模型抄写长引文时的常见区间）：

| 单条失败率 | N=5 | N=10 | N=15 | N=20 |
|---|---|---|---|---|
| 2% | 90% | 82% | 74% | 67% |
| 5% | 77% | 60% | **46%** | 36% |
| 10% | 59% | 35% | 21% | 12% |

一份正常简历抽 10–15 个技能 + 2–4 个项目是常态，落进「有一半概率报错」的区间 ——
用户感知就是「有时能过、有时过不了」。**条目越多越容易挂**，也解释了为什么简单简历很少出问题。

**额外的坑**：`ai.py::complete_model` 的重试只在两种情况触发 —— `AppError.retryable`（超时 / 5xx / 429）
与 JSON 解析失败 / pydantic 校验失败。`verify_quotes` 是在 `complete_model` **返回之后**才调用的，
它的异常压根到不了那个重试环。也就是说：

> `docs/teamflow/20261031-r1-dev-skill-coach/TECHNICAL.md:102` 写的
> 「命中失败 → 抛 `AI_SCHEMA_INVALID`（`ai.py` 已重试 1 次）」是**错的**，
> 实际一次都没重试过，用户看到的那次失败就是他唯一的机会。

（该行已在本轮修正。）

## 3. 根因二：`_squash` 只去空白 → 把「同一句话的不同写法」当成编造

原实现是 `"".join(text.split())`。`str.split()` 按 `str.isspace()` 切分，
而**下面这些字符 `isspace()` 为假**，所以会原样留在比对串里：

| 字符 | 码位 | 来历 | `isspace()` |
|---|---|---|---|
| 软连字符 | `U+00AD` | **pypdf 在行尾断词处就会留下它**（`micro-` / `service` 跨行） | False |
| 零宽空格 | `U+200B` | PDF 排版、网页复制粘贴常见 | False |
| 零宽非连接符 / 连接符 | `U+200C` / `U+200D` | 部分导出工具、emoji 序列 | False |
| BOM | `U+FEFF` | DOCX / TXT 带 BOM 保存 | False |
| word joiner | `U+2060` | 排版防断行 | False |

这些字符**模型看不见，也就不会复制**。于是正文里带着、`source_quote` 里没有：

```
正文：负责 micro<U+00AD>service 架构设计与落地     ← 抽取产物
引用：负责 microservice 架构设计与落地              ← 模型抄的
```

`_squash` 之后两者不相等 ⇒ 判成「找不到出处」。而**只有引用恰好跨过那个不可见字符时才会失败**，
引用落在干净段落里就能通过 —— 这是第二个「概率性」来源，而且它跟模型完全无关。

同理，模型很爱把 `（）：` 写成 `():`，内容一个字没改，原实现也判死。

## 4. 修法：先归一化，再三级降级

### 4.1 归一化口径（`_squash`）

```python
unicodedata.normalize("NFKC", text)          # 抹平全半角与兼容字形（（）→()、：→:）
    → 丢掉 category == "Cf" 的字符            # 一次性覆盖上表全部不可见字符
    → 丢掉所有 isspace() 为真的字符           # 原有的「去空白」保留
```

两边（正文与引用）走同一个函数，所以**只抹平「同一段文字的不同写法」，不会抹平改写**：
把「负责」改成「主导」仍然判没命中（`test_nfkc_normalization_does_not_swallow_real_differences`）。

另外容忍**尾部省略号**（`…` / `⋯` / `...`）：模型抄到一半用省略号收尾是截断，不是编造。
只放宽末尾 —— 中间出现省略号说明它拼接了两段不相邻的原文，照样判没命中
（`test_ellipsis_in_the_middle_is_not_tolerated`）。

### 4.2 失败降级（`_draft_with_sources`）

| 步骤 | 行为 | 失败时 |
|---|---|---|
| 1 | 抽草稿，算 `unsourced_labels` | 干净 → 直接返回，**只调 1 次模型，成本与时延不变** |
| 2 | 有没命中的：**补抽一次**，把「哪几条没命中」写进提示（`QUOTE_REPAIR_HINT`） | 模型能针对性纠正，比笼统「请重试」有效得多 |
| 3 | 补抽反而更差（没命中条数变多）→ 丢弃补抽结果，拿第一版继续 | 不拿更烂的草稿去赌 |
| 4 | 逐条剔除（`drop_unsourced`），只剔除站不住的 | 记为 `profile.quote_dropped` warning，带条数与被剔的名字 |
| 5 | 一条都不剩 → 502（可重试） | 那不是抄写偏差，是整份在编，重试才有意义 |

`verify_quotes` **保持严格**（一条不合格即抛），继续做最终闸门；
它在 `generate_profile` 里排在剔除之后，正常路径不会触发，作用是「剔除逻辑哪天被改坏」的回归防线。

## 5. 为什么这不违反 anti-goal 1

PRD 里 anti-goal 1 的原话是「**画像里列出用户从未掌握的技能**，且 `sourceQuote` 为空或与简历原文对不上」。
约束的对象是**落库的画像**，不是「这一次请求」。

- 旧实现：一条不合格 → 整份不落库 → 画像里确实没有无源之词，但**用户拿不到任何画像**；
- 新实现：那条不合格的**不入库** → 画像里依然没有无源之词，用户还能拿到其余合规部分。

两者都满足 anti-goal 1，新实现只是把「整份作废」换成了「剔掉那一条」。
代价是**静默少一条能力项**，所以剔除会落一条 warning 日志（`profile.quote_dropped`）便于事后排查。

## 6. 用户侧还能做什么

归一化能吃掉的只是「同一段文字的不同写法」。以下情况仍会（也应该）失败：

- 扫描件 / 图片版 PDF：抽不出文本层（`EMPTY_FILE`，提示换 TXT / DOCX）；
- 双栏或表格排版：PDF 抽出的阅读顺序被打乱，模型按语义连续抄 —— 抄出来的是**它理解后的顺序**，
  不是文件里的顺序，仍可能对不上；
- 模型把两三段拼成一句：中间会出现省略号或直接缺字，属于改写，会被拒。

内网单机部署遇到反复失败时，先看后端日志里有没有 `profile.quote_miss` / `profile.quote_dropped`：
- 只有 `quote_miss` 没有 `quote_dropped` → 补抽就修好了，属正常；
- 两者都有且条数不少 → 大概率是这份 PDF 的抽取质量太差，换 DOCX 或 TXT 重新上传。
