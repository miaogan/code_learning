# PRD · 题库多维标签 + 熟练度过滤（r6）

## 1. 背景与目标

### 1.1 现状（已读代码确认）

- 题库是静态文件 `backend/app/seed/questions.json`（80 题：前端 / 后端 / 算法与数据结构 / 计算机基础 各 20；`single` 48 / `multiple` 20 / `text` 12；`difficulty` basic 72 / challenge 8），字段仅 `id/direction/kind/difficulty/prompt/options/answer`，**没有「是否必备」维度，也不在数据库里**。
- 组卷在 `backend/app/services/exam.py`：按画像 `tech_stack + target_role` 算方向相关度后**确定性排序**取题。同画像同题库 → 同一份卷。
- 后果（用户痛点）：反复练的用户会记住答案，**练的是记忆而不是能力**；成长时间线的分数因此不可信。
- 判分纯本地零 AI（10s 内出分），答案只活在 `runs.payload`；诊断报告按「方向 / 面试题型」聚类 3–5 条短板（证据链 = 题目 id + 得分）。

### 1.2 目标（可度量的结果）

1. 题库成为**可查询的数据**（SQLite），带齐 `direction / kind / difficulty / essentiality` 四个维度，且标签有**可复现的回填规则**，不是凭感觉。
2. 用户在某题上「短期内答对多次」后，**下一次笔试不再考该题**；超过窗口未练则**自动回流可考**。
3. 「过滤」**永不成为新的故障源**：任何题量不足都由文档化的兜底阶梯消化，**绝不因过滤返回 400 把用户卡死**。
4. 同时修掉「卷子雷同」：同相关度内随机抽题 + 排除最近 3 次已出过的题。
5. 既有能力零回归：本地判分 10s、报告证据链、面试多轮（r5）、时间线（r3）、润色、复制 Markdown。

## 2. 用户故事

**US-1（复练者）** 我在同一个方向反复练了几天，想让卷子别再考我已经会的东西。
- 验收条件：某题 30 天内被我答对 2 次且最近一次正确 → 之后连续 5 次出卷都不含该题（除兜底阶梯已记录回流）；该题时间被推到 31 天前 → 重新出现在可考池。

**US-2（被卡住的用户）** 我几乎把某个方向的题都做熟了，也**不能**因为这样就出不了卷。
- 验收条件：构造「某方向题目全部熟练」与「近 3 卷覆盖池子大半」两种极端，出卷仍返回 HTTP 200、题数 ≥10、客观 ≥8、挑战 ≤20%，页面上不出现任何「题库不足」错误。

**US-3（想看到进步的复练者）** 我不想再抽到和上两次一样的题。
- 验收条件：同画像连续两次出卷不完全相同；连续 4 次出卷时第 4 份不含前 3 份出过的题（池子允许时）。

**US-4（产品/团队）** 维度标签要能拿去做后续功能，而不是一堆随手填的字符串。
- 验收条件：80 题四维标签全部非空且在闭集内，`essentiality` 三档皆有、每方向必备题 4–10 道、必备题至少覆盖 2 种题型；回填规则以「id → 档位」确定性映射写进技术方案。

**US-5（用户可解释性）** 卷子变了，我至少能知道为什么。
- 验收条件：本次过滤了 N>0 道熟练题时，笔试页显示一行「本次已过滤 N 道你已熟练掌握的题」；N=0（如已全库兜底）时不显示任何断言性文案。

## 3. 范围与非目标

### 3.1 本轮范围

- **A 题库入库 + 多维标签**：SQLite 表承载 80 题；幂等迁移（首次启动/脚本导入，重复执行不重复插入）；补齐 `essentiality`，把 `difficulty` 扩到三档 `basic/intermediate/challenge`；回填规则文档化。
- **B 熟练度与过滤**：单用户每题熟练度记录（滑动窗口内答对次数、最近答对时间、最近一次是否正确、累计作答次数）；熟练判定；组卷过滤；6 层兜底阶梯；随机抽题 + 近 3 卷去重；阈值集中配置。
- **C 契约与回归**：必要字段双侧同步（`schemas.py` ↔ `types.ts`，snake_case）；既有能力零回归；门禁只增不减。
- **D 轻量可解释性**：笔试页一行过滤说明（仅 N>0 时）；配套 ≤1 页设计说明。

### 3.2 非目标（本轮明确不做）

- **不做题库/熟练度管理界面**（不做后台管理系统、不做 CRUD、不做熟练度看板）。**理由**：本产品是单用户成长应用，题库是产品资产而非用户数据，管理入口无用户价值、却要为此引入鉴权、表单校验、批量编辑与一整套 UI 设计，成本与风险远高于本轮收益；本轮用户价值全部来自「过滤生效」本身。**后续入口**：①诊断报告页新增「已掌握 / 待突破」子视图（读同一份熟练度数据，只读展示）；②若将来题库需要运营侧维护，再单独立「题库管理」需求（含权限模型）。
- **不做按必备度/难度加权组卷**：`essentiality` 本轮只用于**兜底回流优先级**（必备题回流更晚、更保守），`difficulty` 只用于既有「挑战题 ≤20%」；「必备题优先 / 难度配比」留后续需求。
- **不做多人/多租户**：沿用仓库既有单用户模型，熟练度全局一份，不引入 `user_id` 与权限。
- **不引入新依赖、不引入外部数据库、不做 SQL 迁移框架**。
- **不改面试链**（r5 多轮对话与四项配置）**、不做 AI 出题**（判分与组卷保持纯本地零 AI）。
- **不改报告口径**：短板聚类维度、证据链（题目 id + 得分）、课程直连均不动。
- **不为随机化引入「同画像同卷」的复现开关**（生产每次不同；测试用可注入随机源）。

## 4. anti-goals / 反面目标

以下四种结果，**测试全绿也算失败**（都可由使用者直接观察到）：

1. **过滤静默生效**：用户发现「反复练的那批题不见了」，但页面上没有任何说明，于是他判断「题库变小了 / 出卷坏了」并来投诉。→ 判定：连续两次笔试卷面题量与方向明显变化，而页面上找不到一句解释。
2. **熟练度算成「累计计数」**：30 天前答对的题一直被算作熟练，用户想复练却再也考不到（功能本意是「短期熟练才过滤」）。→ 判定：把作答时间推到 31 天前后，题目**在卷面上没有回流**；或答错一次后该题仍被继续过滤。
3. **兜底把过滤变成噪音**：只要凑题稍有不足就整体退回全库，用户连续两份卷子里都是刚练熟的题——功能在职、效果为零。→ 判定：在一份「应该有过滤」的卷子里，熟练题数量与未过滤时无差别，且 payload/文案都说不清用了哪一层。
4. **随机化顺手把卷子结构随机掉**：为了「不雷同」，同一用户两次总分从 80 掉到 40、报告短板整体换了一批，历史分数彻底不可比。→ 判定：随机后仍出现「客观题 7 道」「挑战题 3 道（>20%）」或两次卷子的方向分布完全不同。

## 5. 交互流程摘要

1. 上传简历 → 画像（不变）。
2. 点「开始笔试」→ 服务端选池：可考池 = 全库 −（熟练题）−（最近 3 卷出过的题）→ 同相关度同难度档内**随机**抽题 → 结构闸门（10–12 题 / 客观 ≥8 / 挑战 ≤20% / 方向覆盖 ≥2）→ 不足则按 **6 层兜底阶梯**逐级放宽 → 出卷。
3. 卷面顶部（`sc-page-sub` 区域）在 N>0 时显示一行「本次已过滤 N 道你已熟练掌握的题」；N=0 不显示。
4. 答题 → 提交 → **本地判分**（零 AI，10s 内）→ 逐题对错写入 payload → **写熟练度事件**（仅客观题；简答题不计分不写）→ 出总分 / 时间线事件 / 报告（口径不变）。
5. 下次笔试：熟练题按窗口规则被过滤；超窗或最近答错的题自动回流。

## 6. 需求细则

### 6.1 题库数据（维度与闭集）

| 字段 | 闭集 / 说明 |
|---|---|
| `id` | 保留原 id（`fe-*` / `be-*` / `algo-*` / `cs-*` 之类前缀），历史 payload 反查必须命中 80/80 |
| `direction` | 前端 / 后端 / 算法与数据结构 / 计算机基础（各 20，与现状一致） |
| `kind` | single / multiple / text（48 / 20 / 12） |
| `difficulty` | basic / **intermediate**（本轮新增档）/ challenge（challenge 保持 8 道） |
| `essentiality` | **must_know / advanced / nice_to_know**（必备 / 进阶 / 加分） |
| `prompt` / `options` / `answer` | 原样迁入；`answer` 只存库与服务端 payload，不进任何响应模型 |
| `source` | seed（本轮全部）/ ai（预留，本轮不产 AI 题） |
| `active` | 默认全部启用；停用题不参与组卷（本轮不提供界面开关） |
| `created_at` | 入库时间（ISO 字符串，与既有表一致） |

**essentiality 语义（回填口径，供技术方案落成 id 级映射表）**：
- `must_know`：该方向从业者面试/笔试**必问的通用基础概念**（不会就不该被当成「合格」）。
- `advanced`：需要**实操经验或组合知识**才能答对（不是背书能过）。
- `nice_to_know`：偏细节 / 冷门 / 记忆型加分项。

**回填必须满足的可验证约束**（防止「标签 = 某个既有字段的投影」）：三档皆非空；每个方向 `must_know ∈ [4,10]`；全部 `must_know` **至少覆盖 2 种 kind**；`difficulty` 三档皆非空且 challenge 恰 8；映射以「id → 档位」表写入技术方案。

### 6.2 熟练度与判定（用户已选定口径）

- 记录粒度：**每题一行（单用户）**；需要能精算**滑动窗口**——窗口内答对次数、最近答对时间、最近一次是否正确、累计作答次数。
- 熟练判定：**最近 30 天内答对 ≥2 次，且最近一次作答正确 → 熟练**；任一条件不满足 → 可考。**窗口必须是真实滑动窗口**（30 天前答对的那一次不能算进次数）；恰好 30 天前的作答算窗口内（含边界）。
- 自动回流：超过 30 天未练 → 回流；**最近一次答错 → 立即回流可考**。
- 必备题**不豁免**：`must_know` 熟练后同样被过滤（仅在兜底阶梯里比 `advanced`/`nice_to_know` 更晚回流）。
- 简答题（`text`）不计分（既有口径恒定 false），因此**不参与熟练判定、永不被熟练过滤**——这是刻意的，不另造「已作答即熟练」的伪口径。
- 阈值集中配置、**代码里不出现散落魔数**：窗口天数 30、答对次数 2、近期去重卷数 3（均可用环境变量覆盖，默认值单一出处）。

### 6.3 兜底阶梯（唯一实现，顺序即契约）

停止条件（每层判定）：**10–12 题 ∧ 客观 ≥8 ∧ 挑战 ≤20% ∧（池子允许时）覆盖 ≥2 个方向**；命中即停，不再往下走。

| 层 | 取题口径 |
|---|---|
| L1 | 基线：排除熟练题 + 排除最近 3 卷已出题 + 本卷内不重复 |
| L2 | 回流**已熟练的 `must_know`** 题（补进卷面） |
| L3 | 回流**其他已熟练题** |
| L4 | 放松「最近 3 卷」排除：从最旧的一卷起逐卷放宽（仍禁止本卷内重复） |
| L5 | 跨方向补题（题量优先于方向纯度，承接 r1 既有口径） |
| L6 | 全库兜底：忽略熟练过滤与历史排除（仍禁止本卷内重复、仍守客观 ≥8 / 挑战 ≤20%） |

- 只有 **L6 仍不足**（即题库本身不够）才允许 400「题库不足，暂无法出卷，请稍后重试」（既有中文文案）；**任何一层因过滤而不足都不得 400**。
- 每次出卷在 `runs.payload` 记录本次选池事实（所用层 `stage`、过滤掉的题数 `filtered_count`、各层回流题数），QA 凭 payload 断言阶梯命中顺序；旧 payload 无该字段不得报错（读侧一律给默认值）。

### 6.4 契约

- 新增/变更字段双侧同步：`backend/app/schemas.py` ↔ `frontend/src/api/types.ts`，snake_case；`ExamRun` 新增 `filtered_count: int`（默认 0，旧响应对齐）；难度联合类型补 `intermediate`；`essentiality` 是否需要暴露给前端由技术方案定，**但两侧闭集必须逐字一致**。
- 错误统一 `{error:{code,message,retryable}}`、message 中文、不含路径/堆栈/端点/Key。
- 样式只用 `frontend/src/styles/tokens.css` 变量、无裸色值（**注意 `test_engineering_gates.py` 的「无裸色值」断言连 CSS 注释里的色值字面量也算**）。

## 7. 验收标准（本任务夹内编号）

### P0

**AC-1 题库入库 + 幂等迁移**
- 启动（`init_db()` 路径）后题库表可查出 **80 行**；另提供脚本导入路径。两条路径都执行两次后行数仍为 80、无重复 id。
- 幂等语义：**已存在的行不覆盖、不删除**（`INSERT ... ON CONFLICT DO NOTHING` 语义），只补缺失行；迁移不修改既有 `runs/profiles/reports/timeline_events` 数据、不删旧库、零新依赖。
- 历史 payload 中的题目 id **80/80** 可在库内反查命中。
- 表结构含 §6.1 全部字段；`options`/`answer` 以 JSON 文本列存；`answer` 不出现在任何响应模型（含新接口）。
- DDL 只在 `db.py`、SQL 只在 `repository.py`；`seed/questions.json` 仍是唯一题库来源（DB 由它导入，不手工双写）。

**AC-2 标签齐全且回填可复现**
- 80 题 `direction/kind/difficulty/essentiality` 全部非空且在闭集内；四方向各 20；kind = 48/20/12；`difficulty` 三档皆非空、challenge 恰 8。
- `essentiality` 三档皆非空；每方向 `must_know` 数量 ∈ [4,10]；全部 `must_know` 覆盖 ≥2 种 kind。
- 「id → 三档」映射与判定口径写入该任务夹 TECHNICAL；单测断言上述分布；重复导入后（未手工改库时）标签不变。

**AC-3 维度闭集单一出处 + 双侧契约**
- 四维闭集（direction / kind / difficulty / essentiality / source）集中在后端单一模块（`rules.py` 或 `config.py`），`schemas.py` 与 `types.ts` 的联合类型逐字对齐、snake_case。
- 前端新增/变更类型通过 `npm run typecheck`；无裸色值断言通过。

**AC-4 熟练度记录与写入零副作用**
- 提交判分后按 `per_question` 写入熟练度（**仅客观题**；`text` 不写）；累计作答次数、最近一次是否正确、最近答对时间与窗口内答对次数可从记录算出且互相一致。
- 同一 run 重复提交：仍返回 400 既有文案，且**不产生第二条作答事件**；提交过程异常时不留下半条记录（零副作用，与 r5 AC-10 同风格）。
- 未提交（`status=running`）的卷不产生任何熟练度数据。

**AC-5 熟练判定与阈值配置（逐档可测）**
- 判定为 `最近 30 天内答对 ≥2 次 ∧ 最近一次作答正确`；以下逐档单测：0 次 / 1 次 / 2 次命中 / 2 次但最近一次错 / 2 次都在 31 天前 / 恰好 30 天边界（算窗口内）。
- 判定实现为**纯函数**（输入作答事件 + now），不读真实系统时间，可注入 now 单测。
- 三个阈值（窗口 30 天 / 答对 2 次 / 近期去重 3 卷）只在配置单一出处定义，允许环境变量覆盖；代码中无散落魔数（新增校验或断言证明）。

**AC-6 必备题不豁免**
- `essentiality=must_know` 且熟练的题**同样被过滤**：单测构造后断言卷面不含该题（除非命中 L2+ 且 payload 已记录回流）。

**AC-7 过滤生效与回流（核心证据）**
- 构造「同一题 30 天内答对 2 次且最近正确」→ 之后**连续 5 次出卷均不含该题**（若本次命中了兜底回流，payload 的 `stage` 必须 ≥L2 且回流题数计入）。
- 把该题最近答对时间篡改为 31 天前 → 该题**回流可考**（在池子允许时可出现在卷面）。

**AC-8 兜底阶梯：绝不因过滤 400**
- 六层阶梯按 §6.3 实现且**唯一实现**；每层停止条件为「10–12 题 ∧ 客观 ≥8 ∧ 挑战 ≤20% ∧ 池子允许时 ≥2 个方向」。
- 两类极端场景断言：①某方向全部题熟练；②最近 3 卷覆盖池子大半。两者出卷 **HTTP 200、题数 ≥10、客观 ≥8、挑战 ≤20%**，**不出现任何「题库不足」**。
- 每次出卷 payload 记录 `stage` / `filtered_count` / 各层回流题数；按 payload 可断言阶梯命中顺序（先 L2 后 L3 后 L4 后 L5 后 L6）；旧 payload 读侧给默认值不报错。

**AC-9 随机抽题 + 近 3 卷去重**
- 同画像连续两次出卷**不完全相同**（题集或顺序至少一处不同）；随机只在**同相关度、同难度档**内进行，结构约束（10–12 / 客观 ≥8 / 挑战 ≤20% / 方向覆盖）恒定成立。
- 最近 3 次已出过的题不出现在新卷（L4 未放松前）；连续 4 次出卷断言：第 4 份与前 3 份的题 id **交集为空**（池子允许时）。
- 随机源可注入（单测可复现），生产默认不固定种子。

**AC-10 既有能力零回归**
- 判分仍**纯本地零 AI**、提交后 10s 内出总分、响应无 `answer`；诊断报告证据链（题目 id + 得分）与聚类口径不变。

## 12. 假设与待澄清

- **Q1（口味 · 待定）是否把存量已完成答卷回填为熟练度数据？** 若回填，老用户第一次带过滤出卷就能立刻见效；但存量卷来自「雷同卷」，重复练同一份卷会被算成熟练。**推荐：不回填**（与 r3 时间线「历史数据从本版本起记录」口径一致，口径干净、可测）。若你要回填：需要一次性迁移脚本，且首次出卷过滤更狠、L4+ 兜底更常触发。
- **Q2（口味 · 待定）是否显示 AC-12 的一行「本次已过滤 N 道题」？** 不显示则零契约变更（但反面目标 1「过滤静默」失去唯一解药）。**推荐：显示**（一行、复用既有样式类，成本极低）。若你选择不显示：`ExamRun` 不加 `filtered_count`，本轮少一处双侧契约改动。
- **Q3（口味 · 待定）`essentiality` 初始标注用「确定性规则回填」还是「人工逐题标注 80 题」？** 规则回填可复现、当天完成，但可能与难度/题型强相关（信息量偏低）；人工标注更准，但要一次 80 题领域评审。**推荐：规则回填 + 分布约束**（三档皆非空、每方向必备 4–10、必备覆盖 ≥2 种题型），人工标注列为后续入口。若你要人工标注：本轮工期 +，兜底回流优先级更可信。
- **Q4（口味 · 待定）题量不足时，「新鲜度」与「领域纯度」谁优先？** 即：先放松「最近 3 卷去重」（同领域但可能刚考过）还是先跨领域补题。**推荐：先放松去重**（同领域的新鲜度优先于跨领域补题，与既有「题量优先于方向纯度」一致，且避免卷子方向散成一锅）。若反过来：会更常出现刚考过的同领域题，但方向配比更纯。

> 其余口径已由澄清轮或代码确认，不构成待澄清项：窗口 30 天 / 答对 2 次 / 最近一次正确 / 近 3 卷去重 / 必备题不豁免 / 兜底 6 层且绝不因过滤 400 / 简答题不计分因此永不被熟练过滤 / 单用户全局熟练度 / 不做题库管理 UI / 本沙箱可跑 vitest 与 build。
