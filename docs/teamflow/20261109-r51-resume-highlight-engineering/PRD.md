> 需求来源：用户目标岗位「高级 AI 应用工程师」，希望本项目在简历中构成亮点。
> 任务夹：`docs/teamflow/20261109-r51-resume-highlight-engineering/`（本文件 / TECHNICAL.md / RESUME.md / ACCEPTANCE.md）。
> 状态：**方案阶段**。本轮只落「M1 交付可信度」的产品代码外改动，M2 / M3 按里程碑实施。

## 1. 问题定义

### 1.1 现状（本轮实际核过，不是估计）

| 维度 | 已有 | 证据 |
|---|---|---|
| 内容资产 | 题库 1164 题、教程 40 章、8 方向 × 子方向 × 3 难度 | `seed/questions.json`、`content/tutorials/*.ts` |
| 工程底座 | pytest 633 passed / 1 skipped、vitest 250 passed、ruff / typecheck / lint / build 全绿 | 上一轮实跑；`.github/workflows/ci.yml` 双 job |
| 可靠性 | 异步任务 + 断连恢复 + 部分唯一索引幂等 + AI 超时分级 + 统一中文错误 envelope | `profile_jobs` / `resume_jobs` / `services/ai/ai.py` |
| 可观测性 | `X-Request-Id` 全链路、结构化日志（`ai.response` / `ai.failed`，含 `elapsed_ms` 与失败分类） | `core/observability.py`、`services/ai/ai.py` |
| 交付证据 | GitHub Actions 双 job 已实跑 31 次，最近 `CI #31`（`a54e4be`）成功，#27–#31 连续通过 | [Actions](https://github.com/miaogan/code_learning/actions) |

### 1.2 真实缺口

1. **只有功能，没有证据**：上述能力都是「实现得好」，不是「解决过难题」。面试官 10 分钟能看完功能列表，但看不到「为什么这么选、效果如何、怎么验证」。
2. **可观测数据打完就丢**：结构化日志只进 `logging`，未落库、未聚合、无趋势，无法回答「模型改版后是变好还是变坏」。
3. **交付可信度文档失真**：`ARCHITECTURE.md §7.2` 仍写「CI 已写，未在 GitHub 真跑过」，但实测 Actions 已有 31 次运行、最近 `CI #31`（`a54e4be`）成功，#27–#31 连续通过；本机 `gh` 未认证但网页公开可读。**文档与事实不一致本身才是硬伤**（本轮已更正 §7.1 / §7.2）。
4. **学习计划仍是规则表**：`studyPlan.ts` 靠方向 / 子方向 / 难度做确定性挑选，没有检索、没有召回评估、没有「为什么推荐这一章」的引用归因。

### 1.3 定位纠偏（必须先做，否则简历会翻车）

代码里**没有**向量检索、没有多 Agent 编排、没有评测闭环，AI 侧是 OpenAI 兼容单次调用 + pydantic 校验。
因此简历**禁止**写「自研 RAG 系统 / 多 Agent 平台」——`recall@k`、chunk 策略、编排终止判据都会被追问到穿帮。
正确定位：**LLM 应用工程化与可靠性 + 内容工程**。这个方向比再堆一个聊天功能稀缺得多。

## 2. 目标与非目标

**目标**

- G1：让仓库状态可被第三方验证（绿 CI、可见的取舍论证、可复现的自检命令）。
- G2：把「AI 输出质量」变成可复跑、可回归、可写进简历的**指标**，而不是主观感受。
- G3：把 40 章教程 + 1164 题从「静态内容」变成「可检索、带引用的知识资产」。

**非目标**

- 不引向量数据库、不自研 embedding、不做多 Agent 编排（与本仓库「零外部依赖」取舍冲突，且无法在面试中提供实测数据）。
- 不把离线评测指标包装成「模型质量提升」，两条轨道严格分开（见 TECHNICAL §3.3）。
- 不改题库种子、不改动任何既有 HTTP 契约的必填字段（只做纯附加）。
- 不虚构任何性能指标；所有简历数字必须来自可复跑命令的输出。
