### Q1. 【单选 · 基础 · 必会】 在 Redis 中，需要频繁独立更新用户对象的单个字段（如仅修改昵称），同时希望节省序列化开销并支持部分读取，最适合使用哪种数据结构？

- A. String
- B. Hash ✅
- C. List
- D. Set

**答案**：B　**解析**：Hash 结构允许对对象字段进行独立更新，无需整体序列化/反序列化，且支持部分读取，非常适合字段频繁单独修改的场景。String 适合整存整取的 JSON 对象或计数器，但整体读写大对象时更省内存/更快；List 和 Set 不适合存储对象字段。

### Q2. 【单选 · 进阶 · 必会】 在 Cache-Aside 模式下，写操作通常采用哪种顺序来更新数据库和缓存？

- A. 先更新数据库，再删除缓存 ✅
- B. 先删除缓存，再更新数据库
- C. 先更新缓存，再更新数据库
- D. 先更新数据库，再更新缓存

**答案**：A　**解析**：Cache-Aside 模式写操作的标准做法是先更新数据库，再删除缓存，以避免并发读写导致缓存中长期存在旧值。先删缓存再更新数据库（B）在并发读时可能回填旧值；先更新缓存再更新数据库（C）和先更新数据库再更新缓存（D）都容易因并发写导致缓存与数据库不一致，且更新缓存成本较高。

### Q3. 【判断 · 进阶 · 必会】 缓存击穿是指大量不同的 key 在同一时刻失效，导致请求全部打到数据库。

- A. 正确
- B. 错误 ✅

**答案**：错误　**解析**：题干描述的是缓存雪崩（大量 key 同时失效），而非缓存击穿。缓存击穿特指某个热点 key 失效瞬间，大量并发请求直接打到数据库；缓存穿透则是查询不存在的 key 绕过缓存。因此该陈述错误。

### Q4. 【单选 · 进阶 · 必会】 使用消息队列削峰填谷时，以下哪项措施最能保证消息不丢失？

- A. 生产者设置 acks=all 并重试，broker 配置副本，消费者手动 ack 后再提交 ✅
- B. 生产者发送后不等待确认，消费者自动提交 offset
- C. 仅依靠 broker 的单副本存储，消费者处理完立即删除消息
- D. 生产者批量发送，消费者批量拉取并自动确认

**答案**：A　**解析**：保证消息不丢失需要生产者确认（acks=all）和重试、broker 多副本冗余、消费者手动 ack 确保处理成功后再提交位移。B 项不等待确认和自动提交都可能丢失消息；C 项单副本无冗余，故障即丢失；D 项批量自动确认在异常时可能丢失未处理消息。

### Q5. 【判断 · 进阶 · 必会】 在 Kafka 中，消费组内的一个分区可以同时被多个消费者消费。

- A. 正确
- B. 错误 ✅

**答案**：错误　**解析**：Kafka 消费组内每个分区同一时刻只能分配给一个消费者，这是消费组实现并行消费的基础。若一个分区被多个消费者同时消费，会导致位移提交混乱和重复处理，因此该说法错误。

### Q6. 【单选 · 挑战 · 必会】 关于延迟队列实现方案，以下描述正确的是？

- A. Redis zset 通过轮询 zrangebyscore 获取到期任务，实现简单但存在轮询延迟和压力 ✅
- B. Kafka 原生支持任意精度的延时消息，无需额外组件
- C. 时间轮（如 Netty HashedWheelTimer）持久化能力强，适合生产环境直接保证不丢消息
- D. 生产环境只需使用 Redis zset 即可保证消息不丢失，无需备份或兜底

**答案**：A　**解析**：A 选项正确描述了 Redis zset 方案的特点：score 存到期时间，轮询获取，简单但有延迟和压力。B 选项错误，Kafka 无原生延时，需多 topic 阶梯或外部调度；C 选项错误，时间轮内存高效但持久化弱；D 选项错误，生产需 Redis zset + 备份 DB + 兜底扫描保证不丢。

### Q7. 【单选 · 挑战 · 进阶】 在设计支持读写分离与分库的数据库中间件时，以下关于故障转移和一致性处理的描述正确的是？

- A. 故障转移只需在客户端配置重试，无需健康检查或主从切换
- B. 读从库时，对于关键路径应强制走主库读以保证一致性 ✅
- C. 所有读请求都必须走主库，否则无法保证一致性
- D. 分片键路由只适用于写操作，读操作无需路由

**答案**：B　**解析**：B 选项正确，关键路径强制主库读可避免从库延迟导致的数据不一致。A 选项错误，故障转移需要健康检查、主从切换（如 Orchestrator）和连接重试；C 选项错误，非关键路径可读从库，采用 stale-ok 策略；D 选项错误，读写都需按分片键路由。

### Q9. 【单选 · 基础 · 必会】 关于 CI/CD 流水线，以下哪项最准确地描述了最小可用流水线的阶段顺序？

- A. 拉码 → 依赖安装 → 构建 → 测试 → 打包/部署 → 健康检查 ✅
- B. 拉码 → 构建 → 依赖安装 → 测试 → 打包/部署 → 健康检查
- C. 拉码 → 测试 → 构建 → 依赖安装 → 打包/部署 → 健康检查

### Q10. 【单选 · 基础 · 必会】 在 Nginx 中，关于 upstream 健康检查与失败转移，以下哪项描述是正确的？

- A. proxy_next_upstream 用于在请求失败时转移到下一个 upstream 服务器 ✅

### Q11. 【判断 · 基础 · 必会】 蓝绿部署和金丝雀发布的主要区别在于：蓝绿部署是瞬间全量切换流量，而金丝雀发布是渐进式地放量验证新版本。

### Q12. 【单选 · 进阶 · 必会】 在 Kubernetes 中，一次外部请求要到达某个 Pod，通常经过的组件顺序是？

- A. 客户端 → Service → Ingress Controller → Pod
- B. 客户端 → Ingress Controller → Service → Pod ✅
- C. 客户端 → Pod → Service → Ingress Controller
- D. 客户端 → Deployment → Service → Pod

**答案**：B　**解析**：参考答案指出路径为客户端 → Ingress Controller → Service → Pod（经 kube-proxy/iptables 或 IPVS）。Ingress 负责七层路由/域名，先于 Service 处理外部流量；Service 提供稳定 VIP 与负载均衡，再转发到 Pod。A 把 Service 放在 Ingress 前，不符合七层入口先行的常见路径；C 顺序完全颠倒；D 中 Deployment 是管理副本与滚动更新的控制器，不直接参与请求转发。
